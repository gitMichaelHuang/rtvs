System Overview & Architecture

1.1 What RTVS Does

The RTP Transaction Validator System (RTVS) is a Spring Boot RESTful microservice that simulates a real-time, account-to-account payment network — similar to FedNow or UPI instant-payment rails.

It enforces five core banking constraints before any money moves:

RuleDescription
Sender exists & is ACTIVEBlocked or missing senders are rejected immediately
Receiver exists & is ACTIVECannot credit a non-existent or blocked account
Amount > 0Zero or negative amounts are invalid
Sufficient balanceSender's real-time balance must cover the amount
Daily limit not exceededSum of today's COMPLETED sends + new amount ≤ daily cap

All ledger updates are atomic (ACID): either both the debit and the credit are committed together, or neither is — there is no partial state.

How the Code Works

2.1 Payment Flow — Step by Step

Every POST /api/v1/rtp/payments request passes through this exact sequence. The entire sequence runs inside one database transaction (@Transactional).

1
JWT AuthenticationJwtAuthenticationFilter reads the Authorization: Bearer … header, validates the token, and loads the userId + role into the Spring SecurityContext. Requests without a valid token are rejected with 401 before reaching any controller.
2
Role Check (RBAC)SecurityConfig confirms the caller has ROLE_USER. Analysts and Admins cannot initiate payments.
3
Ownership CheckPaymentService verifies that the JWT's userId equals the request's senderId. A user cannot send money from another person's account (403 if mismatch).
4
Idempotency CheckThe paymentRequestId is a unique client-generated key. If the same ID has already been processed, the original result is returned immediately — no double debit. A UNIQUE database constraint also guards against race conditions.
5
Save INITIATED TransactionA transaction record is written to the database with status INITIATED. This creates an audit trail even if validation later fails.
6
ValidationEngineFive rules are checked in order (see §2.2). On the first failure, a RtvsException is thrown. The catch block in PaymentService marks the transaction REJECTED, saves it, and returns a 200 failure response (no rollback).
7
Status → VALIDATEDIf all five rules pass, the transaction status advances to VALIDATED.
8
Ledger PostingLedgerPostingService debits the sender, credits the receiver, and writes two LedgerEntry rows — all within the same database transaction (see §2.3).
9
Status → COMPLETED & CommitThe transaction is saved as COMPLETED. Spring commits the database transaction, making all changes durable and visible.
✗
System Error PathIf any unexpected exception escapes the catch block (e.g. a DB connection failure during ledger posting), Spring rolls back the entire transaction. No money moves and no incomplete record is left behind.

2.2 Validation Engine

ValidationEngine.validate() is called from inside the payment's @Transactional context, so the database lock acquired here is held until the whole transaction commits.

#CheckFailure Code
1Amount > 0INVALID_AMOUNT
2Sender exists in DBSENDER_NOT_FOUND
3Sender status = ACTIVEACCOUNT_BLOCKED
4Receiver exists in DBRECEIVER_NOT_FOUND
5Receiver status = ACTIVEACCOUNT_BLOCKED
6Pessimistic lock on sender, then balance ≥ amountINSUFFICIENT_FUNDS
7Sum of today's COMPLETED sends + new amount ≤ daily limitDAILY_LIMIT_EXCEEDED
🔒

Concurrent safety: Step 6 issues a SELECT … FOR UPDATE (PostgreSQL row-level lock) on the sender row. Any concurrent payment from the same sender waits until this transaction commits, preventing balance overdrafts under high load.

2.3 Ledger Posting Service

LedgerPostingService.post() performs four writes within the same transaction:

  1. Locks the receiver row (SELECT FOR UPDATE) — prevents concurrent credit race
  2. Decrements sender.currentBalance and saves
  3. Increments receiver.currentBalance and saves
  4. Inserts a DEBIT ledger entry (sender) and a CREDIT ledger entry (receiver)

Each LedgerEntry records the balanceAfter, providing a complete point-in-time audit trail for every cent that moves through the system.

2.4 Security & JWT

The system uses stateless JWT authentication — no HTTP sessions are maintained.

ComponentResponsibility
JwtTokenProviderSigns tokens with HMAC-SHA256 using the secret from application.yaml. Tokens carry sub (userId) and roles claims. Default expiry: 24 hours.
JwtAuthenticationFilterIntercepts every request exactly once. Extracts the Bearer token, validates it, and sets the authentication in Spring's SecurityContext.
SecurityConfigDefines route-level rules and enables method-level security (@PreAuthorize).
UserDetailsServiceImplLoads a UserAccount from the database when authenticating via /auth/login. Maps BLOCKED accounts to a locked Spring Security user.
RolePermissions
ROLE_USERInitiate payments, view own balance, view own history
ROLE_ANALYSTView failed transaction log (read-only)
ROLE_ADMINView failed transaction log; configure limits (future)

Run the following SQL once in pgAdmin or psql to create the database and user:

CREATE DATABASE rtvsdb;
-- If using a dedicated user (optional):
CREATE USER postgres WITH PASSWORD '3893';
GRANT ALL PRIVILEGES ON DATABASE rtvsdb TO postgres;

Swagger UI Testing Guide

4.1 Accessing Swagger

With the application running, open your browser and navigate to:

http://localhost:8080/swagger-ui/index.html

You will see all four endpoint groups: Authentication, Payments, Users, and Transactions.

4.2 Getting a JWT Token

  • Expand the Authentication section
    Click POST /auth/login
  • Click "Try it out"
    The request body editor becomes active.
  • Enter credentials
    {
  "userId":   "U100",
  "password": "password"
}
  • Click "Execute"
    A successful response (HTTP 200) returns: 
    {
  "token":  "eyJhbGciOiJIUzI1NiJ9...",
  "userId": "U100",
  "role":   "ROLE_USER"
}
  • Copy the token value
    Select everything after "token": " up to the closing quote. You will need this in the next step.
⚠️

The token expires after 24 hours. Re-login to get a fresh token if you receive a 401.

4.3 Authorizing Swagger

  • Click the "Authorize 🔒" button
    It appears at the top-right of the Swagger UI page.
  • Paste the token
    In the Value field under the JWT (http, Bearer) scheme, paste your token. Do not include the word "Bearer" — Swagger adds it automatically.
  • Click "Authorize" then "Close"
    All subsequent requests will now include the Authorization: Bearer <token> header automatically.

5.3 Verifying Transactions

-- All transactions
SELECT transaction_id, payment_request_id, sender_id, receiver_id,
       amount, status, failure_reason, transaction_date, created_at
FROM rtp_transactions
ORDER BY created_at DESC;

-- Only completed payments
SELECT * FROM rtp_transactions WHERE status = 'COMPLETED';

-- Only rejections
SELECT transaction_id, sender_id, amount, failure_reason
FROM rtp_transactions
WHERE status = 'REJECTED'
ORDER BY created_at DESC;

5.4 Verifying Ledger Entries

-- All ledger entries with transaction reference
SELECT le.ledger_id, le.user_id, le.entry_type, le.amount,
       le.balance_after, le.created_at, t.payment_request_id
FROM ledger_entries le
JOIN rtp_transactions t ON t.transaction_id = le.transaction_id
ORDER BY le.created_at DESC;

-- Ledger entries for a specific user (full history)
SELECT entry_type, amount, balance_after, created_at
FROM ledger_entries
WHERE user_id = 'U100'
ORDER BY created_at;

For every COMPLETED payment you should see exactly two ledger entries: one DEBIT for the sender and one CREDIT for the receiver, sharing the same transaction_id.

5.5 Useful Audit Queries

-- Daily spend total for U100 today (mirrors the daily-limit logic)
SELECT COALESCE(SUM(amount), 0) AS daily_total
FROM rtp_transactions
WHERE sender_id = 'U100'
AND transaction_date = CURRENT_DATE
AND status = 'COMPLETED';

-- Balance reconciliation: sum of ledger entries should equal current balance
SELECT ua.user_id,
       ua.current_balance AS balance_in_account,
       MAX(le.balance_after) AS last_ledger_balance
FROM user_accounts ua
LEFT JOIN ledger_entries le ON le.user_id = ua.user_id
GROUP BY ua.user_id, ua.current_balance
ORDER BY ua.user_id;

-- Idempotency check: each paymentRequestId should appear only once
SELECT payment_request_id, COUNT(*) AS occurrences
FROM rtp_transactions
GROUP BY payment_request_id
HAVING COUNT(*) > 1; -- should return 0 rows
✅

If the idempotency check returns zero rows, the system is correctly preventing double payments. Every paymentRequestId appears in the table exactly once.

Running Tests & Coverage

6.1 Run All Tests

From the project root, run:

# Run the full test suite
./gradlew test

# Windows
.\gradlew.bat test

Test results are written to build/reports/tests/test/index.html. Open this file in a browser for a visual pass/fail report.

ℹ️

The tests use an H2 in-memory database (configured in src/test/resources/application.yaml). You do not need PostgreSQL running to run the tests.

6.2 Generate JaCoCo Coverage Report

First, add the JaCoCo plugin to build.gradle. Open the file and add these two lines:

// In the plugins {} block, add:
id 'jacoco'

// At the end of build.gradle, add:
test {
    useJUnitPlatform()
    finalizedBy jacocoTestReport   // run coverage after tests
}

jacocoTestReport {
    dependsOn test
    reports {
        xml.required  = true
        html.required = true
    }
}

jacocoTestCoverageVerification {
    violationRules {
        rule {
            limit {
                minimum = 0.80   // 80% minimum per spec
            }
        }
    }
}

Then run:

# Run tests + generate HTML coverage report
./gradlew test jacocoTestReport

# Run tests + verify 80% minimum coverage threshold
./gradlew test jacocoTestCoverageVerification

6.3 Reading the Coverage Report

  • Open the report
    Navigate to build/reports/jacoco/test/html/index.html and open it in any browser.
  • Top-level summary
    The summary row shows overall instruction, branch, and line coverage across the project. Green = ≥ 80%, yellow = 50–80%, red = < 50%.
  • Drill into packages
    Click a package name (e.g., com.example.rtvs.service) to see per-class coverage.
  • View source highlighting
    Click a class name to see the exact lines covered (green) and missed (red). Use this to identify which edge cases need more tests.
