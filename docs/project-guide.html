What Is This System?

RTVS stands for Real-Time Validation Service. It simulates the backend of a payment network — think of what happens server-side when you Zelle or Venmo someone money. The system exposes a REST API that lets authenticated users:

  • Send money from their account to another user's account
  • Check their account balance
  • View their transaction history
  • Query failed transactions (restricted to admin/analyst roles)

The interesting engineering happens inside a single payment: the system has to validate business rules, prevent race conditions when two payments happen simultaneously, update two account balances atomically, and write an immutable audit trail — all in one database transaction that either fully succeeds or fully rolls back.

Industry Term — REST API

REST (Representational State Transfer) is a style for designing HTTP services. A REST API exposes resources (payments, users, transactions) at URLs, and callers manipulate them using standard HTTP verbs: POST to create, GET to read, PUT/PATCH to update, DELETE to remove. The server never stores session state — each request carries everything the server needs to process it.

Architecture Overview

The project follows a layered (n-tier) architecture. Every HTTP request passes through a fixed sequence of layers, and each layer has exactly one responsibility:

🌐
HTTP / Client
Postman, a browser, or another service sends a JSON request over the network.
↓
🔒
Security Layer — JwtAuthenticationFilter, SecurityConfig
Validates the JWT token. Checks the caller has permission for this endpoint. Stops unauthorized requests here — the layers below never see them.
↓
📡
Controller Layer — PaymentController, PaymentControllerV2, …
Parses the HTTP request. Validates the request body shape (@Valid). Calls the service. Wraps the result in an HTTP response. Nothing more.
↓
⚙️
Service Layer — PaymentService, ValidationEngine, LedgerPostingService
All business logic lives here. Orchestrates validation, transaction management, and ledger posting. Has no knowledge of HTTP.
↓
📦
Repository Layer — UserAccountRepository, RtpTransactionRepository, …
Translates between Java objects and database rows. Services call repository methods; SQL is generated automatically by Spring Data JPA.
↓
🗄️
Database — PostgreSQL (production) / H2 (tests)
Stores the three core tables: user_accounts, rtp_transactions, ledger_entries.
Why So Many Layers?

The biggest payoff is testability. Because the service layer has zero knowledge of HTTP, you can test all business logic by just calling Java methods — no web server needed. You can swap PostgreSQL for an in-memory H2 database in tests without changing a single line of business logic. And a new developer can find any piece of logic immediately because everything has a designated home.

Tech Stack

Java 21

The programming language. Version 21 is a Long-Term Support (LTS) release, meaning it gets security patches for years. It introduced records, pattern matching, and sealed classes — none of which this project uses yet, but they're available.

Spring Boot 4

A framework that wires up a production-ready application for you. Without it, you'd manually configure a web server, a database connection pool, a JSON serializer, a security filter chain… Spring Boot auto-configures all of this from your dependencies and application.yaml.

Spring Security

A framework for authentication (who are you?) and authorization (what are you allowed to do?). It plugs into the request pipeline via a chain of filters that run before your controller code.

Spring Data JPA + Hibernate

JPA (Jakarta Persistence API) is a standard interface for talking to a relational database using Java objects. Hibernate is the implementation. Spring Data adds a layer on top that generates common SQL queries automatically from method names like findByPaymentRequestId.

JWT (JSON Web Tokens)

A compact, signed token the client sends with every request to prove identity. The server never stores sessions — it just checks the token's signature. Issued by POST /auth/login and sent as Authorization: Bearer <token>.

Lombok

An annotation processor that generates repetitive Java boilerplate at compile time. @Data generates getters/setters/equals/hashCode. @Builder generates a fluent builder. @RequiredArgsConstructor generates a constructor for final fields. The generated code is invisible in the source but real in the bytecode.

The Security Layer

How JWT Authentication Works

When a user logs in via POST /auth/login, the server checks their password and returns a JWT token. Every subsequent request must include this token. The server never looks up the user in a database to verify requests — instead, it verifies the token's cryptographic signature.

1

Client logs in

POST /auth/login with {"username":"U100","password":"password"}. Spring Security's AuthenticationManager verifies the password against the BCrypt hash stored in the database.

2

Server issues a JWT

If the password matches, JwtTokenProvider.generateToken() creates a signed token containing the user's ID and roles. The token is signed with HMAC-SHA256 using a secret key — anyone can read the token's payload, but only the server can produce a valid signature.

3

Client stores the token

The client stores the token (in memory, in local storage, etc.) and sends it with every subsequent request in the Authorization: Bearer <token> header.

4

Filter intercepts every request

JwtAuthenticationFilter extends OncePerRequestFilter — Spring calls it for every HTTP request, exactly once. It extracts the token, validates the signature, and loads the user's identity into the SecurityContext.

5

SecurityConfig authorizes the request

After the filter sets the identity, Spring Security checks the route rules in SecurityConfig. POST /api/v1/rtp/payments requires ROLE_USER. If the identity has that authority, the request proceeds to the controller. If not, Spring returns 401 (no token) or 403 (wrong role).

JwtAuthenticationFilter.java
@Component                                      // 1
@RequiredArgsConstructor
public class JwtAuthenticationFilter
        extends OncePerRequestFilter {          // 2

    private final JwtTokenProvider tokenProvider;

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain)
            throws ServletException, IOException {

        String token = extractBearerToken(request); // 3

        if (StringUtils.hasText(token)
                && tokenProvider.validateToken(token)) {

            String userId =
                tokenProvider.getUserIdFromToken(token);
            List<SimpleGrantedAuthority> authorities =
                parseAuthorities(
                    tokenProvider.getRolesFromToken(token));

            UsernamePasswordAuthenticationToken auth =
                new UsernamePasswordAuthenticationToken(
                    userId, null, authorities);    // 4

            SecurityContextHolder
                .getContext()
                .setAuthentication(auth);          // 5
        }

        filterChain.doFilter(request, response);   // 6
    }
}
1@Component
Tells Spring to create and manage an instance of this class. Spring discovers it via classpath scanning at startup.
2OncePerRequestFilter
A Spring base class guaranteeing the filter runs exactly once per HTTP request, even if the request is forwarded internally.
3extractBearerToken
Reads the Authorization header and strips the "Bearer " prefix, returning just the JWT string.
4UsernamePasswordAuthenticationToken
Spring Security's representation of a confirmed identity. Constructor: (principal, credentials, authorities). Credentials are null after authentication — we don't need the password anymore.
5SecurityContextHolder
A thread-local storage slot for the current user's identity. Everything downstream (controllers, services) can read it via authentication.getName().
6filterChain.doFilter
Passes the request to the next filter in the chain. Filters form a pipeline — you must call this or the request is silently dropped.

The Controller Layer

Controllers are the entry points for HTTP requests. They do exactly three things: parse input, call a service, return output. They contain no business logic.

PaymentController.java
@RestController                       // 1
@RequestMapping("/api/v1/rtp/payments")// 2
@RequiredArgsConstructor
@Tag(name = "Payments", ...)          // 3
@SecurityRequirement(name = "JWT")
public class PaymentController {

    private final PaymentService paymentService; // 4

    @PostMapping                      // 5
    @Operation(summary = "...")
    public ResponseEntity<PaymentResponse>
            initiatePayment(

        Authentication authentication) {            // 7

        return ResponseEntity.ok(
            paymentService.processPayment(
                request,
                authentication.getName())); // 8
    }

1@RestController
Combines @Controller (this class handles web requests) and @ResponseBody (return values are serialized to JSON automatically, not rendered as HTML templates).
2@RequestMapping
The base URL path for all endpoints in this class. Every method inside inherits this prefix.
3@Tag / @Operation
OpenAPI (Swagger) annotations. They add metadata to the auto-generated API documentation at /swagger-ui.html. They have zero effect at runtime.
4private final PaymentService
Dependency injection. The final + @RequiredArgsConstructor combination means Lombok generates a constructor that receives this as a parameter — Spring injects the value at startup.
5@PostMapping
Binds this method to POST /api/v1/rtp/payments. Spring routes matching requests here.
6@Valid @RequestBody
@RequestBody tells Spring to deserialize the JSON body into a PaymentRequest object. @Valid triggers Jakarta Bean Validation — if any @NotBlank/@NotNull constraint fails, Spring returns 400 immediately without calling this method.
7Authentication authentication
Spring injects the Authentication object from the SecurityContextHolder that the JWT filter populated. No extra code needed.
8authentication.getName()
Returns the "principal" — the user ID string that was stored in the JWT's subject claim. This is passed to the service for ownership verification.

The Full Payment Flow

Here is what happens, step by step, when a client sends POST /api/v1/rtp/payments:

🌐 HTTP POST /api/v1/rtp/payments
Body: paymentRequestId, senderId, receiverId, amount, currency
↓
🔒 JwtAuthenticationFilter — validates token, sets SecurityContext
If invalid → 401
↓
🔒 SecurityConfig — checks ROLE_USER on POST /api/v1/rtp/payments
If wrong role → 403
↓
📡 PaymentController.initiatePayment() — @Valid checks pass?
If invalid body → 400
↓
⚙️ PaymentService.processPayment() — opens @Transactional boundary
↓
① Ownership check — senderId == authenticated user?
If not → AccessDeniedException (403)
↓
② Idempotency — find existing record for paymentRequestId?
If found → return original result immediately
↓
③ Create RtpTransaction in INITIATED state → save to DB
↓
④ ValidationEngine.validate() — acquires pessimistic DB lock on sender
Throws RtvsException → REJECTED
↓
⑤ LedgerPostingService.post() — deduct sender, credit receiver, write entries
↓
⑥ Mark transaction COMPLETED → save
↓
📡 PaymentController wraps result → ResponseEntity.ok(response)
↓
🌐 HTTP 200 OK — JSON body: transactionId, status, postedAt

The Service in Detail

PaymentService.java (core logic)
@Service
@RequiredArgsConstructor
public class PaymentService {

  private final ValidationEngine validationEngine;
  private final LedgerPostingService ledgerPostingService;
  private final RtpTransactionRepository transactionRepository;

  @Transactional                               // 1
  public PaymentResponse processPayment(
        PaymentRequest request,
        String authenticatedUserId) {

    if (!authenticatedUserId
            .equals(request.getSenderId())) { // 2
        throw new AccessDeniedException("...");
    }

    Optional<RtpTransaction> existing =
        transactionRepository
          .findByPaymentRequestId(
            request.getPaymentRequestId());   // 3
    if (existing.isPresent()) {
        return toResponse(existing.get());
    }

    RtpTransaction transaction =
        RtpTransaction.builder()             // 4
          .transactionId(
              UUID.randomUUID().toString())
          .status(TransactionStatus.INITIATED)
          // ... other fields
          .build();

    transactionRepository.save(transaction); // 5

    try {
        UserAccount lockedSender =
            validationEngine.validate(request);// 6
        transaction.setStatus(VALIDATED);

        ledgerPostingService
            .post(transaction, lockedSender); // 7

        transaction.setStatus(COMPLETED);
        transactionRepository.save(transaction);

        return PaymentResponse.builder()
            .transactionId(tx.getTransactionId())
            .status("COMPLETED")
            .build();

    } catch (RtvsException e) {              // 8
        transaction.setStatus(REJECTED);
        transaction.setFailureReason(
            e.getReasonCode());
        transactionRepository.save(transaction);

        return PaymentResponse.builder()
            .status("REJECTED")
            .reasonCode(e.getReasonCode().name())
            .build();
    }
  }
}
1@Transactional
Spring wraps this method in a database transaction. If an unchecked exception propagates out, every database write inside rolls back. See the Transactions section for deep detail.
2Ownership check
Even though SecurityConfig verified the user has ROLE_USER, it doesn't know which user the sender is. This check prevents U100 from sending money out of U200's account.
3Idempotency check
paymentRequestId is a client-provided unique ID. If the client retries (due to a timeout), we return the original result instead of processing twice. The DB column is UNIQUE to enforce this at the database level too.
4Builder pattern
RtpTransaction.builder()...build() is the builder pattern from Lombok's @Builder. It lets you construct objects with named parameters in any order, which is far more readable than a 10-argument constructor.
5Early save (INITIATED)
Saving the transaction before validation captures a record even if validation fails. The transaction lifecycle: INITIATED → VALIDATED → COMPLETED (or REJECTED at any point).
6ValidationEngine
Checks 6 business rules in order and acquires a pessimistic write lock on the sender account. Returns the locked sender for use in ledger posting.
7LedgerPostingService
Updates both account balances and writes immutable debit/credit ledger entries — the double-entry bookkeeping record of the transaction.
8catch (RtvsException)
Business rule failures (insufficient funds, etc.) are caught here and recorded as REJECTED. Critically: this does not rethrow, so @Transactional does NOT roll back — the REJECTED record is committed to the DB intentionally.

The Service Layer

ValidationEngine — Six Business Rules

The ValidationEngine runs six checks in sequence. It throws RtvsException on the first failure. This is the "fail fast" pattern — no point checking the daily limit if the sender doesn't exist.

ValidationEngine.java — the six checks
public UserAccount validate(PaymentRequest request) {

    // 1 — Amount > 0 (belt-and-suspenders check; @Valid already caught this)
    if (request.getAmount().compareTo(BigDecimal.ZERO) <= 0)
        throw new RtvsException(INVALID_AMOUNT, "...");

    // 2 — Sender exists and is ACTIVE
    UserAccount sender = userAccountRepository.findById(request.getSenderId())
            .orElseThrow(() -> new RtvsException(SENDER_NOT_FOUND, "..."));
    if (sender.getStatus() == AccountStatus.BLOCKED)
        throw new RtvsException(ACCOUNT_BLOCKED, "...");

    // 3 — Receiver exists and is ACTIVE
    UserAccount receiver = userAccountRepository.findById(request.getReceiverId())
            .orElseThrow(() -> new RtvsException(RECEIVER_NOT_FOUND, "..."));
    if (receiver.getStatus() == AccountStatus.BLOCKED)
        throw new RtvsException(ACCOUNT_BLOCKED, "...");

    // 4 — Acquire PESSIMISTIC WRITE LOCK on sender row in the DB
    //      No other transaction can modify this row until ours commits
    UserAccount lockedSender = userAccountRepository
            .findByIdForUpdate(request.getSenderId()).orElseThrow(...);

    // 5 — Sender has enough balance (checked on the LOCKED row)
    if (lockedSender.getCurrentBalance().compareTo(request.getAmount()) < 0)
        throw new RtvsException(INSUFFICIENT_FUNDS, "...");

    // 6 — Daily limit not exceeded (sum of today's COMPLETED transactions)
    BigDecimal dailyTotal = transactionRepository.sumDailyAmount(
            request.getSenderId(), LocalDate.now(), TransactionStatus.COMPLETED);
    if (dailyTotal.add(request.getAmount())
                  .compareTo(lockedSender.getDailyLimit()) > 0)
        throw new RtvsException(DAILY_LIMIT_EXCEEDED, "...");

    return lockedSender; // Return the locked account for use in ledger posting
}

LedgerPostingService — Double-Entry Bookkeeping

Real banking systems never update a balance in place — they write immutable ledger entries. Every payment produces exactly two entries: a DEBIT from the sender and a CREDIT to the receiver. The current balance is the sum of all entries. RTVS stores both: it caches the balance directly on the account row (for fast lookup) and writes the audit trail entries.

LedgerPostingService.java
public void post(RtpTransaction transaction, UserAccount lockedSender) {
    BigDecimal amount = transaction.getAmount();

    // Lock the receiver account too (prevents concurrent credit race)
    UserAccount receiver = userAccountRepository
            .findByIdForUpdate(transaction.getReceiverId()).orElseThrow(...);

    BigDecimal senderBalanceAfter   = lockedSender.getCurrentBalance().subtract(amount);
    BigDecimal receiverBalanceAfter = receiver.getCurrentBalance().add(amount);

    // Update cached balances
    lockedSender.setCurrentBalance(senderBalanceAfter);
    userAccountRepository.save(lockedSender);
    receiver.setCurrentBalance(receiverBalanceAfter);
    userAccountRepository.save(receiver);

    // Write the immutable audit trail
    LedgerEntry debit = LedgerEntry.builder()
            .ledgerId(UUID.randomUUID().toString())
            .userId(transaction.getSenderId())
            .entryType(EntryType.DEBIT)
            .amount(amount)
            .balanceAfter(senderBalanceAfter)
            .build();

    LedgerEntry credit = LedgerEntry.builder()
            .ledgerId(UUID.randomUUID().toString())
            .userId(transaction.getReceiverId())
            .entryType(EntryType.CREDIT)
            .amount(amount)
            .balanceAfter(receiverBalanceAfter)
            .build();

    ledgerEntryRepository.saveAll(List.of(debit, credit));
}
Why Not Just Update the Balance Directly?

The ledger entries are append-only — they are never modified or deleted. This means you can always reconstruct every account's balance history from scratch, audit every cent that ever moved, and detect data corruption (if balanceAfter on entry N doesn't equal balanceAfter on entry N-1 plus the amount, something is wrong). This is the standard pattern in any financial system.

The Repository Layer

The repository interfaces don't contain implementation code. Spring Data JPA reads the interface at startup and generates proxy classes that implement the methods using SQL it figures out from the method signatures and annotations.

RtpTransactionRepository.java
public interface RtpTransactionRepository
        extends JpaRepository<RtpTransaction, String> { // 1

    // 2 — Spring generates:
    // SELECT * FROM rtp_transactions
    // WHERE payment_request_id = ?
    Optional<RtpTransaction> findByPaymentRequestId(
            String paymentRequestId);

    // 3 — Custom JPQL query (Java object syntax, not table names)
    @Query("SELECT t FROM RtpTransaction t " +
           "WHERE (t.senderId = :userId OR " +
           "       t.receiverId = :userId) " +
           "AND t.transactionDate BETWEEN :from AND :to " +
           "ORDER BY t.createdAt DESC")
    List<RtpTransaction> findByUserIdAndDateRange(
            @Param("userId") String userId,
            @Param("from") LocalDate from,
            @Param("to") LocalDate to);

    // 4 — Aggregation query
    @Query("SELECT COALESCE(SUM(t.amount), 0) " +
           "FROM RtpTransaction t " +
           "WHERE t.senderId = :senderId " +
           "AND t.transactionDate = :date " +

    BigDecimal sumDailyAmount(
            @Param("senderId") String senderId,
            @Param("date") LocalDate date,
            @Param("status") TransactionStatus status);
}
1JpaRepository<T, ID>
Extending this interface gives you save(), findById(), delete(), findAll(), and pagination methods for free. T is the entity type; ID is the type of its primary key.
2Derived query methods
Spring Data reads the method name and generates the SQL. findBy + PaymentRequestId → WHERE payment_request_id = ?. This works for simple cases and saves a lot of boilerplate.
3@Query with JPQL
For complex queries, use @Query with JPQL (JPA Query Language). It looks like SQL but operates on entity class names and field names, not table/column names. Hibernate translates it to the correct SQL dialect.
4COALESCE(SUM(...), 0)
If no rows match (no transactions today), SUM returns NULL. COALESCE converts NULL to 0, avoiding a NullPointerException when the result is compared to the daily limit.

The Pessimistic Lock

UserAccountRepository.java
public interface UserAccountRepository
        extends JpaRepository<UserAccount, String> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)   // 1
    @Query("SELECT u FROM UserAccount u WHERE u.userId = :userId")
    Optional<UserAccount> findByIdForUpdate(@Param("userId") String userId);
}
Industry Term — Pessimistic Locking

The problem: Two payment requests arrive simultaneously, both from U100 who has $500. Both read the balance as $500 and both decide $400 is fine. Both subtract $400. U100 is now at -$300. This is called a lost update and it's a classic race condition.

The solution: SELECT ... FOR UPDATE (what PESSIMISTIC_WRITE translates to) places an exclusive lock on the row. The second transaction must wait until the first commits or rolls back before it can read or write the row. Once the first transaction subtracts $400 and commits, the second reads the real balance of $100 and correctly rejects the payment.

It's called "pessimistic" because we assume conflict will happen and lock preemptively. The alternative, optimistic locking, assumes conflicts are rare and only detects them at commit time.

Domain Entities

Domain entities are the Java classes that map directly to database tables. JPA manages the translation between the Java world and the SQL world.

RtpTransaction.java
@Entity                                    // 1
@Table(name = "rtp_transactions")          // 2
@Data                                      // 3
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class RtpTransaction {

    @Id                                    // 4
    @Column(name = "transaction_id")
    private String transactionId;

    @Column(name = "payment_request_id",
            unique = true, nullable = false) // 5
    private String paymentRequestId;

    @Column(precision = 19, scale = 4,
            nullable = false)              // 6
    private BigDecimal amount;

    @Enumerated(EnumType.STRING)           // 7
    @Column(nullable = false)
    private TransactionStatus status;

    @Enumerated(EnumType.STRING)
    @Column(name = "failure_reason")
    private FailureReasonCode failureReason;

    @Column(name = "transaction_date")
    private LocalDate transactionDate;     // 8

    @Column(name = "created_at",
            nullable = false)
    private Instant createdAt;             // 9

1@Entity
Marks this class as a JPA entity. Hibernate will manage its persistence — creating the table (if ddl-auto: update) and generating SQL for CRUD operations.
2@Table(name = ...)
Maps the class to a specific table name. Without this, JPA would default to the class name converted to snake_case.
3@Data, @Builder, @NoArgsConstructor, @AllArgsConstructor
Four Lombok annotations. @Data generates getters/setters/equals/hashCode/toString. @Builder adds the builder pattern. @NoArgsConstructor is required by JPA (it uses reflection to create instances). @AllArgsConstructor is required by @Builder.
4@Id
Marks this field as the primary key. Here we use a UUID string generated in application code, not a database auto-increment integer. This is deliberate: UUIDs are globally unique and can be generated before inserting, which avoids a DB round-trip.
5unique = true
Adds a UNIQUE constraint to the column in the database. Even if application code has a race condition and two threads try to insert the same paymentRequestId, the database will reject the second one with a DataIntegrityViolationException.
6BigDecimal for money
double and float use binary floating point, which cannot represent 0.1 exactly. BigDecimal stores the exact decimal representation. precision=19, scale=4 means up to 15 digits before the decimal and 4 after — enough for large transaction amounts.
7@Enumerated(EnumType.STRING)
Without this, JPA stores the enum's ordinal (0, 1, 2…). If you ever reorder the enum values, all your data silently means different things. EnumType.STRING stores the name ("COMPLETED") — safe to add/reorder enum values.
8LocalDate vs Instant
LocalDate is a calendar date with no time (2024-03-15). Used here for the daily-limit query: "sum all completed transactions for sender on this date." Instant is an absolute point in time with nanosecond precision, stored in UTC.

Transactions, ACID, and @Transactional

A database transaction is a group of operations that must all succeed or all fail together. The acronym ACID describes the four guarantees:

A — Atomicity

Either every operation in the transaction succeeds (committed), or none of them do (rolled back). A payment that crashes halfway through won't debit the sender without crediting the receiver.

C — Consistency

The database moves from one valid state to another. Constraints like NOT NULL, UNIQUE, and foreign keys are enforced. The total money in the system doesn't change — one account loses exactly what the other gains.

I — Isolation

Concurrent transactions don't see each other's in-progress changes. The pessimistic lock enforces this for the sender's balance — a concurrent payment must wait for our lock to release.

D — Durability

Once a transaction commits, it's permanent — even if the server crashes one millisecond later. PostgreSQL writes to a write-ahead log (WAL) before confirming a commit.

What @Transactional Actually Does

@Transactional is processed by Spring's AOP (Aspect-Oriented Programming) proxy. Spring wraps the annotated method in a proxy object. When you call paymentService.processPayment(), you're actually calling the proxy, not the method directly:

What Spring generates (conceptually)
// What Spring generates at runtime (conceptual — actual proxy is bytecode):
public PaymentResponse processPayment(PaymentRequest req, String userId) {
    Connection connection = dataSource.getConnection();
    connection.setAutoCommit(false);              // BEGIN TRANSACTION
    try {
        PaymentResponse result =
            actualPaymentService.processPayment(req, userId); // your code
        connection.commit();                      // COMMIT
        return result;
    } catch (RuntimeException e) {
        connection.rollback();                    // ROLLBACK on unchecked exception
        throw e;
    } finally {
        connection.close();
    }
}
Important: Checked vs Unchecked Exceptions

By default, @Transactional only rolls back on unchecked exceptions (subclasses of RuntimeException). If you throw a checked exception (one that extends Exception directly), the transaction commits. RtvsException extends RuntimeException, but it's caught inside the method, so the transaction does NOT roll back — the REJECTED record is committed intentionally.

Idempotency

Industry Term — Idempotency

An operation is idempotent if calling it multiple times with the same input produces the same result as calling it once. For payments, this prevents double-charging when a network timeout causes a client to retry a request it thinks failed, but the server actually processed.

The pattern works in two layers:

  1. Application layer: PaymentService looks up paymentRequestId first. If found, returns the stored result without processing.
  2. Database layer: The payment_request_id column has a UNIQUE constraint. Even if two threads simultaneously pass the application-level check, only one INSERT will succeed. The other gets DataIntegrityViolationException, which is caught and handled — the code re-reads the now-existing record and returns it.

Error Handling

The project separates two kinds of failures: business failures (not enough money) that result in a 200 OK with "status":"REJECTED", and system errors (server crash, invalid input) that return 4xx/5xx HTTP codes.

GlobalExceptionHandler.java
@RestControllerAdvice   // 1
public class GlobalExceptionHandler {

    // 2 — @Valid failures → 400 Bad Request
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Map<String, Object>> handleValidation(
            MethodArgumentNotValidException ex, HttpServletRequest request) {
        String message = ex.getBindingResult().getFieldErrors()
                .stream().map(e -> e.getField() + ": " + e.getDefaultMessage())
                .findFirst().orElse("Validation failed");
        return buildError(HttpStatus.BAD_REQUEST, message, request);
    }

    // 3 — Ownership violation → 403
    @ExceptionHandler(AccessDeniedException.class)
    public ResponseEntity<Map<String, Object>> handleAccessDenied(
            AccessDeniedException ex, HttpServletRequest request) {
        return buildError(HttpStatus.FORBIDDEN, ex.getMessage(), request);
    }

    // 4 — Catch-all → 500
    @ExceptionHandler(Exception.class)
    public ResponseEntity<Map<String, Object>> handleGeneral(
            Exception ex, HttpServletRequest request) {
        log.error("Unhandled exception: {}", ex.getMessage(), ex);
        return buildError(HttpStatus.INTERNAL_SERVER_ERROR, "Internal server error", request);
    }
}
Why @RestControllerAdvice?

Without it, every controller would need its own try/catch blocks, and inconsistencies would creep in (one controller returns a string, another returns a JSON object, a third crashes with a stack trace). @RestControllerAdvice is a single place that intercepts exceptions from all controllers and converts them into consistent JSON error responses.

Dependency Injection

This is the concept that most confuses people coming from self-contained scripts. In industry codebases, most classes do not create their own dependencies. Instead, they declare what they need, and a framework (Spring's IoC container) creates everything and wires it together.

Without DI (what you might write first)

public class PaymentController {
    // ❌ Hard-coded dependency
    // Cannot be tested without a real DB
    // Cannot swap implementations

The DTO Pattern

Industry Term — DTO (Data Transfer Object)

A DTO is an object whose only purpose is to carry data across a boundary — from the HTTP request to the service, or from the service back to the HTTP response. DTOs are distinct from domain entities (the database-mapped objects).

Consider what would happen if the controller accepted UserAccount directly from the HTTP body: the client could send a password field and overwrite it. Or the response could accidentally expose the password hash. DTOs give you an explicit contract for what the API accepts and returns, independent of what the database stores.

PaymentRequest (DTO — input)
  • paymentRequestId
  • senderId
  • receiverId
  • amount
  • currency
  • note

Annotated with validation constraints. Never touches the DB.

PaymentResponse (DTO — output)
  • transactionId
  • status
  • postedAt
  • reasonCode
  • message

@JsonInclude(NON_NULL) — null fields don't appear in JSON output. A COMPLETED payment has no reasonCode field at all.

API Versioning

The project uses URL-path versioning: /api/v1/rtp/payments and /api/v2/rtp/payments. V1 is completely unchanged. V2 adds an optional processingMode field (STANDARD or EXPRESS) and returns extra fields in the response.

The V2 controller is a pure adapter — it maps the V2 request into a V1 request, calls the existing PaymentService unchanged, then maps the V1 response into a V2 response. Zero service logic is duplicated:

PaymentControllerV2.java — adapter pattern
@RestController
@RequestMapping("/api/v2/rtp/payments")
public class PaymentControllerV2 {

    private final PaymentService paymentService;  // Same service as V1

    private static final Map<ProcessingMode, Integer> COMPLETION_SECONDS =
            Map.of(ProcessingMode.STANDARD, 5, ProcessingMode.EXPRESS, 1);

    @PostMapping
    public ResponseEntity<V2PaymentResponse> initiatePayment(
            @Valid @RequestBody V2PaymentRequest request,
            Authentication authentication) {

        // 1 — Adapt V2 request → V1 request
        PaymentRequest v1Request = toV1Request(request);

        // 2 — Call the UNCHANGED PaymentService
        PaymentResponse v1Response =
            paymentService.processPayment(v1Request, authentication.getName());

        // 3 — Adapt V1 response → V2 response (add processingMode + seconds)
        return ResponseEntity.ok(toV2Response(v1Response, request.getProcessingMode()));
    }

    private V2PaymentResponse toV2Response(PaymentResponse v1, ProcessingMode mode) {
        boolean completed = "COMPLETED".equals(v1.getStatus());
        return V2PaymentResponse.builder()
                // ... all V1 fields ...
                .processingMode(mode)
                // Only set for COMPLETED — @JsonInclude(NON_NULL) hides it for REJECTED
                .estimatedCompletionSeconds(
                    completed ? COMPLETION_SECONDS.get(mode) : null)
                .build();
    }
}
Why This Approach to Versioning?

The alternative — duplicating the entire service layer for V2 — creates two codebases to maintain. A bug fix to the payment logic would have to be applied twice. By making the V2 controller an adapter, the business logic lives in exactly one place. When V3 arrives, another adapter layer is all that's needed.

Testing Strategy

The project has four layers of tests, each with a different scope:

Unit Tests

Test one class in isolation. All dependencies are mocked with Mockito. No Spring context, no database. Extremely fast.

Web Layer Tests

Test the controller + security config with MockMvc. Spring context is loaded but services are mocked. No database.

BDD — Cucumber

Full integration tests expressed in plain English (Gherkin). Real HTTP calls, real database (H2). Run separately with ./gradlew cucumberTest.

Contract Tests — Pact

Define and verify API contracts between consumer and provider. Consumer generates a JSON pact file; provider verifies against it. Run with ./gradlew pactConsumerTest pactProviderTest.

1@ExtendWith(MockitoExtension.class)
Activates Mockito's JUnit 5 extension. It processes @Mock and @InjectMocks annotations before each test. No Spring context is loaded — this is a pure Java test.
2@Mock
Creates a fake implementation of the interface that records calls and returns whatever you configure with when(...).thenReturn(...). By default, all methods return null/0/empty.
3@InjectMocks
Creates a real instance of PaymentService and injects the mocks above into its constructor. This is the class under test — everything else is controlled.
4when(...).thenReturn()
Configures the mock: "when this method is called with this argument, return this value." This controls what the service sees from the repository without touching a real database.
5thenAnswer(inv -> inv.getArgument(0))
More flexible than thenReturn: the lambda receives the actual invocation and returns its first argument (the entity passed to save()). This mimics what a real repository does.
6AssertJ
assertThat(...).isEqualTo(...) is AssertJ's fluent assertion API. It produces readable failure messages and is preferred over JUnit's assertEquals in modern projects.
7verify()
Checks that a mock method was actually called with specific arguments. This verifies that the service correctly passed the locked sender account to the ledger posting service — not just that it returned the right response.

1@WebMvcTest
Loads only the Spring MVC slice: the specified controller, its filters, and the web configuration. Does NOT load services, repositories, or the database. Much faster than @SpringBootTest.
2@Import
@WebMvcTest excludes @Configuration classes by default. We explicitly import SecurityConfig so the security rules are active — otherwise all requests are permitted and the 401/403 tests would be meaningless.
3MockMvc
Lets you simulate HTTP requests without starting a real web server. It exercises the full controller + filter stack but stays in-process. The result is fast and debuggable.
4@MockitoBean
Replaces the Spring bean in the application context with a Mockito mock. Different from @Mock: this is registered in the Spring context, so the controller's injected service is the mock.
5@WithMockUser
Populates the SecurityContextHolder with a fake user. You don't need a real JWT — Spring Security test support short-circuits the filter and injects this user directly.

7andExpect()
Chains assertions onto the result. status().isOk() asserts HTTP 200. jsonPath("$.transactionId") uses JSONPath expression syntax to navigate the response JSON — $ is the root, .transactionId is a field.

Contract Testing with Pact

Industry Term — Contract Testing

In a microservices architecture, Service A (the consumer) calls Service B (the provider) over HTTP. If Service B changes its API, Service A breaks — but you only find out in production. Contract testing solves this: the consumer writes a "pact" (a contract document describing what it expects), and the provider's CI pipeline verifies it actually delivers what the contract specifies. The contract is the shared source of truth.

The workflow has two phases:

1

Consumer test generates the pact file

The consumer test uses Pact's MockServer instead of calling the real provider. It defines what request it will send and what response shape it needs. Pact writes this to build/pacts/rtvs-payment-consumer-rtvs-payment-provider.json.

2

Provider test verifies the pact

The provider test starts the real Spring Boot application, reads the pact file, and replays each interaction against the running server. The @State methods set up the correct DB state before each interaction. The @TargetRequestFilter injects a real JWT so the real security layer passes.

PaymentConsumerPactTest.java (excerpt)
@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "rtvs-payment-provider")
public class PaymentConsumerPactTest {

    // Define the contract: given this state, when I send this, I expect this shape back
    @Pact(consumer = "rtvs-payment-consumer")
    public V4Pact successfulPaymentPact(PactDslWithProvider builder) {
        return builder
            .given("U100 has sufficient funds")
            .uponReceiving("a valid payment request from U100 to U200")
            .method("POST").path("/api/v1/rtp/payments")
            .body(new PactDslJsonBody()
                .stringValue("paymentRequestId", "PR-PACT-001")
                .stringValue("senderId", "U100")
                .stringValue("receiverId", "U200")
                .numberType("amount", 100.00)           // "any number" matcher
                .stringValue("currency", "USD"))
            .willRespondWith().status(200)
            .body(new PactDslJsonBody()
                .stringType("transactionId", "TX-abc123") // "any string" matcher
                .stringValue("status", "COMPLETED"))      // exact match
            .toPact(V4Pact.class);
    }
}
Why Type Matchers Instead of Exact Values?

The consumer doesn't care which transactionId string the provider returns — it just needs a string. Using stringType() instead of stringValue() makes the contract flexible: the provider can generate any UUID and the contract still passes. Exact matching is only used where the exact value genuinely matters (e.g., "status":"COMPLETED").

Design Patterns Reference

Repository Pattern

Abstracts data access behind an interface. The service calls transactionRepository.save(tx) without knowing or caring whether the underlying store is PostgreSQL, H2, or a future NoSQL database. The interface is the contract; the implementation is swappable.

Builder Pattern

Constructing an object with many fields using a chained API: RtpTransaction.builder().transactionId(...).status(...).build(). Avoids telescoping constructors (one for each combination of optional fields) and makes code self-documenting because each field is named at the call site.

Adapter Pattern (V2 Controller)

Converts one interface into another. PaymentControllerV2 adapts the new V2 request/response DTOs to the existing PaymentService interface without changing either. The service is unaware that a V2 version exists.

Template Method Pattern (@Transactional proxy)

Spring's transaction proxy wraps your method in a fixed sequence: begin → execute → commit/rollback. You fill in just the "execute" step; Spring provides the template around it. This is implemented via AOP (Aspect-Oriented Programming) — a proxy object wraps your service transparently.

Fail-Fast Validation

ValidationEngine throws on the first failed check. It does not accumulate all errors. For a payment, this is intentional — there is no value in knowing both that the sender is blocked AND that they have insufficient funds. Stop at the first problem, record it, move on.

Idempotency Key Pattern

The client generates a unique ID per payment intent and includes it in every attempt. The server uses it to deduplicate retries. This is the standard pattern for safe retries on financial APIs — used by Stripe, PayPal, and every major payment provider.
