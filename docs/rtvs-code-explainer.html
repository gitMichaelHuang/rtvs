RTP Transaction Validator System

A Spring Boot 4 backend service for real-time payment validation, ledger posting, and audit.

Java 21 Spring Boot 4.0.3 PostgreSQL JWT Auth HikariCP OpenAPI / Swagger

What is RTVS?

RTVS (Real-Time Payment Transaction Validator System) is a REST API that lets users send money between accounts instantly. Every payment request goes through a strict validation pipeline before funds move, and every successful transfer is recorded in a double-entry ledger.

Key capabilities:

  • Payment processing — initiate, validate, and complete fund transfers atomically
  • Balance & limit enforcement — real-time balance checks and daily spend caps
  • Double-entry ledger — every transfer creates a DEBIT and a CREDIT entry
  • Idempotency — duplicate requests return the original result safely
  • Audit log — analysts and admins can query all failed transactions by date range
  • JWT-based security — role-differentiated access for users, analysts, and admins

Architecture

The application follows a classic layered architecture. Each layer has one responsibility and depends only on the layer below it.

Payment Processing Flow

All payment logic runs inside a single @Transactional context in PaymentService.processPayment(). Either everything commits or everything rolls back.

Happy Path (COMPLETED)

1. Ownership check
Verify senderId == authenticatedUserId. Throws AccessDeniedException if mismatch.
2. Idempotency check
Query paymentRequestId. If already exists, return the cached PaymentResponse immediately — no reprocessing.
3. Create RtpTransaction (INITIATED)
Persist a new transaction record. If a race condition causes a duplicate key error, the existing transaction is fetched instead.
4. ValidationEngine.validate()
Run all 6 business rules in order (see Validation section). Returns the pessimistically-locked sender account on success.
5. Status → VALIDATED
Transaction record updated to VALIDATED before ledger posting.
6. LedgerPostingService.post()
Lock receiver, subtract from sender, add to receiver, save DEBIT + CREDIT ledger entries atomically.
7. Status → COMPLETED · COMMIT
Transaction saved as COMPLETED. The entire operation commits. PaymentResponse(COMPLETED) returned.

Rejection Path (REJECTED)

When ValidationEngine throws RtvsException, PaymentService catches it, sets the transaction status to REJECTED with the failure reason code, and saves it. This is intentionally not a rollback — the REJECTED record is committed so the failure is auditable.
ValidationEngine throws RtvsException
e.g. INSUFFICIENT_FUNDS, ACCOUNT_BLOCKED, DAILY_LIMIT_EXCEEDED…
CATCH → Status → REJECTED
failureReason set; transaction saved as REJECTED.
COMMIT (as REJECTED) · Return PaymentResponse(REJECTED)
No funds moved. reasonCode + message included in response.

Validation Engine

ValidationEngine.validate() runs six checks in sequence. The first failure throws RtvsException and stops processing. The sender account is locked at step 4 (pessimistic write lock) to prevent concurrent balance changes during steps 5 and 6.

#CheckFailure CodeLock held?
1Amount > 0INVALID_AMOUNTNo
2Sender exists & is ACTIVESENDER_NOT_FOUND / ACCOUNT_BLOCKEDNo
3Receiver exists & is ACTIVERECEIVER_NOT_FOUND / ACCOUNT_BLOCKEDNo
4Acquire PESSIMISTIC_WRITE lock on senderSENDER_NOT_FOUNDLock acquired
5Sender balance ≥ amountINSUFFICIENT_FUNDSYes
6Daily outflow + amount ≤ dailyLimitDAILY_LIMIT_EXCEEDEDYes
Daily limit formula:
SELECT COALESCE(SUM(amount), 0) FROM rtp_transactions WHERE sender_id = ? AND transaction_date = ? AND status = 'COMPLETED'
If existing daily total + new amount > dailyLimit, the transaction is rejected.

Ledger Posting

LedgerPostingService.post(transaction, lockedSender) runs within the same @Transactional context as the payment flow. The sender account lock is already held from ValidationEngine; this service acquires a lock on the receiver too.

  1. Lock receiver — findByIdForUpdate(receiverId)
  2. Calculate balances
    • Sender new balance: currentBalance − amount
    • Receiver new balance: currentBalance + amount
  3. Update accounts — save both UserAccount records
  4. Create ledger entries
    • DEBIT entry: userId=senderId, entryType=DEBIT, balanceAfter=senderNew
    • CREDIT entry: userId=receiverId, entryType=CREDIT, balanceAfter=receiverNew
    • Both entries share: transactionId, amount, createdAt=now, ledgerId=UUID
  5. Batch persist — saveAll([debit, credit]) in one query

Other Services

Handles login. Delegates credential validation to Spring Security's AuthenticationManager, then calls JwtTokenProvider.generateToken(). Returns a JWT plus userId and role.

BalanceService

Simple read-only lookup. Finds the UserAccount by userId, throws ResourceNotFoundException (404) if absent, and returns a BalanceResponse.

TransactionService

Queries transactions where the user is sender or receiver within the date range, ordered newest-first. Adds a direction field (DEBIT/CREDIT) based on which side the user is on.

Returns all REJECTED transactions in a date range. Restricted to ROLE_ANALYST and ROLE_ADMIN only. Used as the audit log endpoint.

JWT System

Three classes collaborate to produce and consume JWT tokens on every request.

JwtTokenProvider

MethodWhat it does
generateToken(Authentication)Creates a signed JWT. Embeds userId as the subject and roles as a claim. Expires after 24 hours (configurable via JWT_EXPIRATION_MS).
getUserIdFromToken(token)Parses the JWT and returns the subject (userId).
getRolesFromToken(token)Parses the JWT and returns the roles claim (comma-separated string).
validateToken(token)Checks signature and expiration. Logs a warning and returns false on any failure.

Algorithm: HMAC-SHA (via JJWT 0.12.6). The key is derived from the JWT_SECRET environment variable (min. 32 characters).

JwtAuthenticationFilter

Extends OncePerRequestFilter — guaranteed to run exactly once per HTTP request.

  1. Extract the Authorization: Bearer <token> header
  2. Validate the token via JwtTokenProvider
  3. Parse userId and roles from the token
  4. Build a UsernamePasswordAuthenticationToken and set it in the SecurityContextHolder
  5. Continue the filter chain

If the token is absent or invalid, the filter proceeds without setting authentication — Spring Security then enforces the configured access rules.

JwtAuthEntryPoint

Called when an unauthenticated request reaches a protected endpoint. Returns HTTP 401 with a JSON body containing timestamp, status, error, message, and path.

Concurrency & Idempotency

Pessimistic Locking

When two payments from the same account arrive simultaneously, the first request to reach findByIdForUpdate holds a database row lock. The second request waits until the first commits. This prevents both requests from reading the same stale balance and both thinking there are sufficient funds.

Lock acquired on sender in ValidationEngine (step 4) → held through balance check → held through LedgerPostingService → released only when the @Transactional method commits.

Idempotency via paymentRequestId

The client must supply a unique paymentRequestId per payment intent. The field has a database-level UNIQUE constraint. If the same ID is submitted again:

  1. PaymentService queries for the existing transaction before doing any work
  2. If found, the original result is returned immediately
  3. If a race condition causes two requests with the same ID to arrive simultaneously, a DataIntegrityViolationException is caught and the existing record is fetched
